Three datasets can look completely normal and still fail in three different ways. An XLOOKUP returns N-A even though the IDs look identical. A date like zero-three slash zero-eight slash twenty-twenty-six changes meaning depending on the computer. And a Power Query duplicate cleanup keeps an older row even after you sorted newest first. In every case, the problem is something you cannot easily see. So the rule for this video is simple: prove the failure, diagnose the invisible cause, fix it, then verify again.

First, the lookup problem. Here the source ID looks like A-B dash two-zero-four-eight, and the lookup ID looks exactly the same. But XLOOKUP says N-A. Before changing the formula, compare the text itself. LEN shows one value has seven characters and the other has eight. That tells us an invisible character exists. Now inspect the final character code with UNICODE. The unexpected value is one-sixty: a non-breaking space.

This matters because Excel's TRIM function is designed for normal ASCII spaces. It does not remove the non-breaking space character one-sixty by itself. A safer cleanup is to replace UNICHAR one-sixty with an empty string, and then apply TRIM. After cleaning the ID, LEN returns seven, and XLOOKUP finds the correct customer. Do not stop at the formula. Compare the cleaned ID and verify the lookup result.

Second, dates. The text zero-three slash zero-eight slash twenty-twenty-six looks obvious until two different cultures interpret it. Under a month-day convention, it can mean March eighth. Under a day-month convention, it can mean the third of August. Power Query uses culture when converting text to dates, so relying on the machine's default regional settings can make the same source produce different results.

The fix is to make the intended culture explicit. In Power Query, choose the date data type using locale, or parse the text with an explicit culture or format. Here the source is day-month-year, so we choose English United Kingdom. Now zero-three slash zero-eight becomes third August, and we verify it against a known source row. The lesson is not to trust how familiar a date looks. Tell the query what the text means.

Third, duplicates. Imagine a customer table with two records for A-one-hundred. You sort UpdatedAt descending so the newest Gold record appears first, then remove duplicates by CustomerID. You expect the first row to survive. But an older Silver record can be preserved instead.

Microsoft documents that Table.Distinct does not guarantee which duplicate row will be preserved. Query folding and optimization can change evaluation. So a visible sort is not always a promise about the row that survives. When your business rule truly requires keep-the-first-row-after-sorting, use a predictable pattern: sort by the business rule, buffer that sorted table, then run Table.Distinct. After buffering, verify that the newest Gold row is the survivor. Use Table.Buffer here for correctness of this specific keep-first pattern, not as a universal performance trick.

These three bugs share one theme: data can look correct while its hidden representation, culture, or evaluation order is different from what you assume. When a lookup fails, compare length and character codes. When a date is ambiguous, make culture explicit. When duplicate removal must keep a particular row, verify evaluation order. The workflow is always the same: prove, diagnose, fix, and verify.
