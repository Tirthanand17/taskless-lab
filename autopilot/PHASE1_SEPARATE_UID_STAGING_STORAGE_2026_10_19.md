# FlowMinute Lab — Disposable Linux separate-UID worker/storage permissions proof

**19 October 2026 | Public DRAFT PR #5 | Existing no-secrets GitHub runner only**

## Architectural gap

The separate-process AF_UNIX staging service originally ran under the same Linux UID as its test client. A socket mode of `0600` blocked unrelated accounts but did not protect the SQLite database from another process belonging to that same UID. For an actual cloud worker boundary, the service must own storage permissions while the least-privileged worker may submit only signed commands.

`OfflineStagingIPCService` now has an **opt-in** `socket_group_gid` parameter restricted to the server process's **current effective GID**. The ordinary mode remains `0600`; the explicitly group-enabled mode creates a `0660` Unix socket. The no-secret, Linux-root-only **CI test fixture** uses disposable *unused numeric UIDs*, never adds system accounts or changes sudoers: the service runs with UID/service-private `db/` directory mode `0700` and SQLite file `0600`, with group-controlled `ipc/` directory mode `0710`. The worker runs under a **different numeric UID** with the authorized socket group; a third numeric UID lacks socket access. In all cases the trusted CI harness is separate and owns the test setup.

The worker's fixed subprocess is given only an IPC socket path and a pre-signed request: it **successfully claims a staging task**, yet a separate fixed DB-permission probe under the same worker UID receives `PermissionError` when attempting to read the SQLite file even when told its path. A third-user probe is denied both DB access and socket connection. The local GitHub branch now has a distinct-OS-UID **real permission boundary under this precise ephemeral test setup**, rather than merely in-process command validation.

The new `autopilot/test_agent_staging_uid_isolation.py` regression uses root **only in an existing public GitHub Actions Ubuntu runner**, through `sudo -n` on own-repo branch pushes. It is explicitly skipped by ordinary developer/non-root test discovery. No laptop, remote service, permanent Linux account, paid resources, production credentials, OAuth or YouTube action is involved.

**Limits:** Numeric UIDs do not create hardened production containers, trusted DB time, a remote cloud service, persistent worker identity/KMS, robust per-cgroup CPU quotas or denial of root/admin users. The test harness starts as root and can still access all disposable files; no hostile root threat model is claimed. A worker with authorized socket access still must present valid HMAC signatures, and signatures here are pre-generated by the trusted test harness, not enrolled via a remote secret manager.
