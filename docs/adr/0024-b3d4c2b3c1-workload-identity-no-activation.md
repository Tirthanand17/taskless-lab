# ADR-0024 — B3d4c2b3c1: federated workload and PostgreSQL TLS activation boundary

**Date:** 2026-11-04 (Asia/Kolkata). **Track:** FlowMinute Branch 2 (unattended, GitHub-only engineering). **Status:** strict offline example IAM/OIDC and PostgreSQL TLS policy contract, **NOT** deployed identity federation, verified JWT, cloud account, provider entitlement, private database, or publishing authorization.

## Why this milestone follows PR #26

Branch 2 has tested three prototype mock inference stages (B3d4c2b1 SQLite crash fence, B3d4c2b2 real-process Postgres 16 transactions, B3d4c2b3a least-privileged Postgres roles) and B3d4c2b3b vault requirement/backup hash and actual CI PostgreSQL logical restoration. Those tests do not establish trust in the cloud workload impersonating a provider or allow unattended production access.

Two remaining fundamental privilege-escalation risks are a cloud identity pool that accepts a malicious pull-request/fork workflow and a private database client that connects with SSL encryption **without verifying the intended server**. AWS IAM and GCP WIF requirements differ and must be treated separately.

## Official primary-source research, checked 2026-11-04

- [AWS IAM OIDC roles](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html): GitHub workload IAM must restrict issuer, audience and subject, preferably specific repositories/branches or protected environments, never a global GitHub OIDC principal. **With GitHub environment-scoped sub, AWS sub alone does NOT prove the branch**; a separately verified GitHub protected environment restriction is required.
- [GCP WIF security best practices](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation): GitHub is a multi-tenant issuer. Bind stable repository and owner identifiers, apply restrictive conditions to ref/workflow/environment/event, prevent identity collisions and avoid broad principal-set access or long-lived service account JSON keys.
- [GCP workload federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation): prefer a short-lived external workload token exchange rather than a static service-account key. An attribute condition string in a public repository is **not** proof that a live workload pool or correct IAM assignment exists.
- [PostgreSQL libpq TLS](https://www.postgresql.org/docs/current/libpq-ssl.html): sslmode=verify-full checks both CA chain and remote hostname. Merely sslmode=require encrypts without strong server identity validation; hostname and independently distributed private root must be verified in a live connection.
- [Gemini API project billing](https://ai.google.dev/gemini-api/docs/billing/): project spend caps are experimental and may lag usage by approximately ten minutes, exposing potential overage. No application-side role policy or three-request count can guarantee zero charges.
- [GitHub Actions OpenID Connect deployment](https://docs.github.com/en/actions/concepts/security/openid-connect): short-lived OIDC trust is conditional on repository/workflow identity. Do **not** grant OIDC token permissions in ordinary untrusted public pull-request test jobs.

## Decision: a no-network, no-credential policy lint with a permanently false activation result

Implement **autopilot/offline_cloud_identity_lint.py** with strict static planned policies for AWS and GCP and tests that reject any privilege expansion. This is an offline readiness-design control, not an executable cloud provisioning adapter or user approval record.

1. **Repository identity:** bind the current public GitHub repository name, numeric repository ID and owner ID (read via the authorized GitHub API), the exact main branch ref, a *hypothetical* owner-approved protected environment named flowminute-prod and the dedicated *hypothetical, not yet deployed* workflow filename. A string copy of these claims is not verified JWT identity.
2. **AWS IAM trust policy:** exact expected JSON Version, one trusted GitHub OIDC federated principal under a sample **fictitious** 12-digit AWS account, one Allow action sts:AssumeRoleWithWebIdentity and exact StringEquals audience sts.amazonaws.com and subject repo:Tirthanand17/taskless-lab:environment:flowminute-prod. Deny wildcard/StringLike, extra statement, wrong issuer, broad audience or cross-account principal. AWS environment-scoped sub does not include ref: the test reports protected environment branch restrictions **UNVERIFIED**, including after hypothetical plan success. Actual deployment must verify real GitHub environment rules and role condition behavior independently.
3. **GCP Workload Identity Federation:** a separate fixture with a fake numeric Google Cloud project number and exact issuer/audience, stable repo/owner ID mappings plus an exact condition binding repository ID, owner ID, refs/heads/main, environment, workflow ref and schedule or workflow_dispatch. Require separate service account scope and no persistent service account keys. Both these settings and the resulting subject are synthetic text; no signed OIDC token, provider IAM or service-account impersonation is performed.
4. **Only two future job event types:** schedule and workflow_dispatch on the protected production environment; expressly reject pull_request, pull_request_target, push, forked repo/ref, wrong workflow, branch, issuer/audience and extra claims. No PR job may exchange OIDC tokens. A later owner-approved unattended scheduler could use schedule, but before production it must be protected by independent repository/environment rules and separate service accounts.
5. **Secret access separation:** exactly one immutable named-version, purpose-specific resource per identity for the inference gateway, protected ledger gateway and YouTube OAuth publisher. Access operations differ by provider: GetSecretValue (AWS) and secretmanager.versions.access (GCP). Reject wildcard project access, mutable latest versions, secret sharing, cross-purpose and extra roles. The sample AWS secret ARNs and GCP secret paths are fixture-only. Real provider IAM binding must be read and checked outside untrusted source code.
6. **Database server identity:** require intended libpq sslmode=verify-full, TLS 1.3 minimum, fixed private hostname, exact runtime DB name/role, independently pinned root-CA digest and private endpoint policy. The .private.example hostname is deliberately unresolvable fixture documentation. No TLS handshake, server hostname certificate matching or database connectivity is performed.
7. **No self-certification:** any claim that real provider billing entitlement, owner data-use consent, GitHub environment rules, private ledger or API key already exists is denied. The aggregated result **always explicitly reports** no independently authenticated OIDC/JWT, no IAM readback, no private vault/key, no verified production DB, no actual provider call, no cloud deployment authorization and no YouTube upload/release.
8. **Public CI privilege safety:** the new .github/workflows/flowminute-b3d4c2b3c1-identity-lint.yml is contents:read only, no id-token:write, no secrets, no environment and no cloud authentication action. Unit tests assert these limitations from the actual workflow text. All signing identities are hypothetical fixture claims; no source data or recipient receives private project context.

## Explicit limitations

This is a **static exact-policy linter**. It cannot cryptographically verify GitHub ID tokens; audit whether the production environment's branch restrictions actually exist; read a live AWS/GCP trust policy, role grants, cloud billing tier or Secret Manager access logs; verify real Postgres TLS certificates; deploy/recover a durable private database; authenticate the real owner/reviewers or guarantee provider non-charging. Even if every policy fixture passes, an attacker could supply invented data unless a separately authenticated cloud/owner retrieval flow verifies it. No component here produces a production entitlement token or calls a live service.

The reference describes a future production workflow filename, but does not create one. It MUST NOT be misread as authorization to add OIDC permissions or cloud secrets to public pull_request workflows.
