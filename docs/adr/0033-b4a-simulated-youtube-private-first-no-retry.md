# ADR-0033 — B4a simulated private-first YouTube publication and no-blind-retry boundary

**Date:** 2026-11-05 IST  
**Status:** Proposed source contract only; NO OAuth, upload, cloud deployment, scheduling or release.  
**Branch:** Branch 2 Autopilot, never the already approved Branch 1 assisted uploader.

## Problem

PR #35 made a manually owner-authorized private S3/KMS storage template and read-only fake AWS preflight available. Real owner cloud IAM, durable actual media, protected workers, rights/authentic human approvals, owner YouTube OAuth and seven-day publishing are **not** in place. Branch 1's existing scripts/publish_youtube.py has assisted upload functions and local pending files; it is NOT an appropriate unattended distributed transaction coordinator. An ambiguous videos.insert response could mean the video already exists, making blind create retries dangerous. A remote "request succeeded" message also cannot prove owner channel ID, processing completion, captions, thumbnail, private scheduling, or identical original uploaded media.

## Official YouTube behavior checked 2026-11-05

- [YouTube resumable-upload protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol): a pending session can be queried via empty PUT and Content-Range bytes */TOTAL; 308 indicates incomplete and Range tells the acknowledged bytes; completed sessions may return the prior completion response. Network errors do NOT prove the preceding upload failed. Session URIs can expire. Never create a new session automatically when an existing attempt is ambiguous.
- [videos.insert](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert) and [videos status fields](https://developers.google.com/youtube/data/reference/rest/v3/videos): explicitly set privacyStatus=private on a real later upload. An omitted status can default to public, and on **2026-11-02** YouTube removed the prior blanket private-only restriction for uploads from unverified API projects; never rely on project-verification status to make uploads private.
- [videos.update](https://developers.google.com/youtube/data/reference/rest/v3/videos/update): status.publishAt must be a **future** time on a still-private, never-previously-published video. When using videos.update, also set privacyStatus=private; a past publishAt can cause immediate publication.
- [videos.list](https://developers.google.com/youtube/data/reference/rest/v3/videos/list): separately inspect the exact video ID, channel ID, privacy/upload status, processingDetails.processingStatus and status.publishAt, plus owner-visible contentDetails.hasCustomThumbnail.
- [thumbnails.set](https://developers.google.com/youtube/data/reference/rest/v3/thumbnails/set) November 3, 2026 update: YouTube Shorts can receive custom thumbnails via API only after video processing succeeds; read back the actual thumbnail status rather than trusting the set response. Thumbnail bytes may need an independent comparison when accessible.
- [captions.list](https://developers.google.com/youtube/data/reference/rest/v3/captions/list): caption status "serving" is separate from source SRT text content; captions.list DOES NOT return the actual caption text, so only a separate download and comparison could prove its content. Caption API requires separately granted scopes.
- [YouTube Data API granular quota](https://developers.google.com/youtube/data/determine_quota_cost): May/June 2026 changes introduced separate videos.insert/search quota buckets; do NOT hardcode obsolete historical per-insert costs. Query the owner's actual Google Cloud quota and account policies before any real API requests; calls may consume quota even if invalid.

## Sequence for a future owner-approved B4 production service (NOT built by this PR)

1. Real channel owner independently approves Google OAuth project/scope, exact publishing channel, limits, schedule, synthetic/altered-content disclosure decision and paid/free quota risk. A protected identity provider/vault exposes only required scope to ONE uploader worker; public GitHub PR/CI and creative agents receive no refresh tokens.
2. Independent human source/claims, licensing, voice, thumbnail, music, captions, originality and full-watch reviewers sign exact SHA256 of each real final H264/AAC MP4, SRT, thumbnail, original source/claim docket and all pinned S3 object VersionIds. This cannot be satisfied by CI's synthetic Ed25519 signatures.
3. Real protected database executes conditional insert on **(owner channel, episode, UTC slot)** and a second uniqueness condition on **(owner channel, final MP4 SHA/context)**. An authenticated one-writer lease and atomic compare-and-swap must be proved across actual separate protected workers, not an in-memory Python dataclass. Record a 'possibly sent' fence BEFORE the first network request. On a crash, leave it uncertain; require external independent human/service reconciliation before any fresh upload attempt.
4. Real protected uploader starts a single resumable videos.insert session with privacyStatus private. Persist encrypted session handle and byte count in protected storage BEFORE transmitting media. On uncertain HTTP, inspect/resume **that same session** as specified by the official API; if session expires or remote identity cannot be reconciled, STOP with manual intervention, never send a second videos.insert.
5. Independently read back private video ID, expected channel and exact approved title/description, processing success and actual custom thumbnail; upload and verify subtitles, then independently download/compare caption contents if available. Do not infer complete original MP4 equality from video metadata alone. Preserve all failures as private.
6. Only after newly authenticated owner/human final approval, use a narrowly controlled videos.update to set future publishAt and privacyStatus private; read back actual status.publishAt equals the required UTC instant. Verify every 11:00/16:00/20:30 IST slot on separate dates and that none conflicts with the real channel's existing uploads. Do not bypass reserved slots or reinterpret expired ones as immediate releases.
7. Store independently anchored remote ID/evidence, watch for processing/restrictions/claim errors, audit actual publication versus schedule, perform seven days/21 unique videos with laptop off. Never equate future schedule, cloud simulation, or a returned video ID with actual publication.

## Exactly what this proposed code implements

- autopilot/youtube_private_first_contract.py is **pure Python**. No API client, secrets, HTTP, video bytes, persistent database or cloud.
- prepare_unapproved_intent requires 4 exact SHA256 fingerprints, explicit channel/episode/title/description, caption language, synthetic-media choice, audience choice, strict future UTC timestamp and exact **short 11:00, long 16:00, short 20:30 IST** positions. A canonical context SHA binds the request. It cannot become a real approval.
- propose_first_attempt returns a **simulation-only** POSSIBLY_SENT_NO_RETRY mock fence, rejecting any existing attempt. Production MUST persist the corresponding fence transaction before any network write: these Python structs alone are NOT atomic and NOT a durable exactly-once guarantee.
- note_returned_id records a **mock-only** reported video identifier without claiming a successful upload.
- inspect_injected_video_readback compares mock video/caption responses for exact ID/channel/title/description, private/future publishAt, processed/upload-status, thumbnail, caption language/serving status, YouTube audience/synthetic choice. Even a completely matching fake fixture always returns **actual_authenticated_youtube_readback=false, source media/caption full text proof=false, durable fence=false, release_authorized=false.**
- Negative tests alter each separate field, spoof the channel, lose/duplicate the receipt, try re-upload, forge release flags and select immediate/wrong IST times. No YouTube scopes or network access.
