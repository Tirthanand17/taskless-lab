# ADR-0036 — Branch 2 B4b3: encrypted synthetic resumable-session checkpoint in real CI Postgres

**Date:** 2026-11-05 IST  
**Status:** Source-only simulated security boundary; never deployed and NO real YouTube URLs, Google OAuth, owner-verified consent, paid AWS/GCP or uploads.

## Problem

Branch 2's owner-controlled unattended publishing target is exactly two Shorts and one long video daily at 11:00, 16:00 and 20:30 IST, without an owner's laptop. The merged B4b1 milestone (PR #37) proved in real disposable PostgreSQL a one-shot intent reservation that is not retried after uncertain response. B4b2 (PR #38) added purely mock status-recovery semantics for an already existing YouTube resumable upload session. Neither proved that an upload-session handle could survive a worker restart without leaking its bearer-equivalent access or allowing a new upload attempt.

The official [YouTube resumable upload guide](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol) requires saving the returned session Location URI (step 2) and checking status on that **same** session using zero-body PUT and Content-Range bytes */N (step 4). That URI is a sensitive capability; never log, commit, email or expose to auditors. The official [PostgreSQL SECURITY DEFINER guidance](https://www.postgresql.org/docs/16/sql-createfunction.html) requires trusted search_path, pg_temp last, and same-transaction revocation of PUBLIC EXECUTE.

## Code and verified test plan

- SQL: autopilot/sql/004_ci_youtube_encrypted_session.sql, after disposable SQL 002 and 003. It creates a private one-row-per-existing-fenced-attempt envelope with PostgreSQL uniqueness by channel/episode and by (fake key_version, AES-GCM nonce). No session key, plaintext, actual Google Location URI or owner access token can be stored in this fixture design.
- Caller role: only fm_ci_gateway may call SECURITY DEFINER seal/retrieve; it has **no direct table rights**. fm_ci_auditor sees only whether a synthetic session was sealed, count of mock store/retrieval audit events and algorithm version; fm_ci_worker receives neither writer nor auditor functions. Every operation is scoped to the original B4b1 channel/episode/context SHA/MP4 SHA/ephemeral fence secret hash. A terminal reported video ID forbids future session retrieval.
- Python autopilot/ci_youtube_encrypted_session_vault.py generates a **random 96-bit nonce** and an in-memory **AES-256-GCM ephemeral test key**. A deterministic canonical associated-data object binds owner channel, episode, immutable B4a intended review/source/media context, MP4 SHA, expected byte length and fake key version. The database stores only nonce, ciphertext + AEAD tag, AAD digest and synthetic fake-handle hash. It cannot decrypt independently. The test accepts **only fake-session:** values; real https:// YouTube resumable URLs are refused by design.
- A stored fake envelope must be committed before the test can generate a synthetic status probe. Recovery from a fresh PostgreSQL client with the same ephemeral **test** key decrypts the fake handle and calls the B4b2 contract to generate an instruction for the same session; no actual HTTP or video bytes are sent. No new YouTube videos.insert is authorized. This is still an in-process key; a truly crashed host that loses it cannot recover until an owner-configured production secret vault exists.
- autopilot/test_ci_youtube_encrypted_session_vault.py uses real disposable PostgreSQL and cryptography to test DB encryption at rest, new-client recovery, 24 competing same-attempt sealing requests (at most one succeeds), session missing, wrong/wiped keys, nonce/ciphertext tampering, forged owner/channel/context or one-shot ticket, role/direct-table privilege denials, SQL-only forged token, real URL rejection, terminal remote video ID, redacted auditor status. Actual CI must fail if any real PostgreSQL test skipped.
- .github/workflows/flowminute-b4b3-encrypted-session-vault.yml runs hosted **postgres:16** in an isolated fake DB named flowminute_fence_ci. It bootstraps original SQL 002 role tests, validates SQL 003 cross-worker fence tests, migrates SQL 004, tests this step and statically checks no network/YT OAuth/AWS provider imported. It uses fake public in-repo CI-only role passwords and sets all publishing/billable switches disabled.

## Explicit safety limitations

A real YouTube session URI can be an account-scoped bearer-like capability. This prototype intentionally rejects real URLs and stores fake strings only, so it cannot prove real URI encryption, KMS binding, authenticated restore, automatic live retry or full backup/replica survival. The simulated session secret key is *ephemeral* and no genuine owner IAM policy, per-user cryptographic segregation, KMS key rotation, credential expiry, S3 provenance evidence, remote approval, immutable audit anchor or secret retention policy is deployed. A Postgres superuser can tamper with mock session rows or audit events (tamper detection tests detect ciphertext modification but do not prevent DB administrator suppression). Mock audit rows do not establish tamper-evidence outside that DB. Cross-worker exact-once intent and encrypted-session recovery are complementary prototypes, not live exactly-once upload delivery.

The next production decision point is **B4c**: owner-specified cloud storage and cost/retention policy, real owner OAuth connection, external key escrow/rotation and private DB persistence, real rights-reviewed video and captions, real user-identity separation and audited API service. These require explicit owner consent and independent deployments; cannot be made true by adding another source-only mock CI suite. Do not disturb Branch 1 assisted YouTube scheduling.

**Branch 2 technical estimate remains ~38% implemented, 62% remaining; genuine independent 21-video unattended proof remains 0/21.** No source-only success should inflate the figure.
